# Nur Al-Quran — Backend & API Reference

This documents the app's actual backend surface: a [Supabase](https://supabase.com)
Postgres database (admin sign-in, feedback, reports, announcements and
anonymous page counts, all behind row-level security) plus a small number of
custom Next.js REST routes. The app has **no end-user accounts**: personal
data (bookmarks, progress, notes, favorites, reading history, settings) is
stored only on the user's device. There is no separate application
server — Supabase's auto-generated [PostgREST](https://postgrest.org) API,
secured entirely by RLS policies and `SECURITY DEFINER` functions, *is* the
backend for everything except audio proxying and the health check.

Quran text, translations, tafsir, reciter audio, and prayer times are never
stored or generated by this app — they are fetched live, on request, from
authoritative third-party APIs (see [External APIs](#external-apis)). This is
deliberate: it keeps religious content sourced from and updatable by its
original providers instead of a copy this app could get out of sync or get
wrong.

## Architecture

```
┌─────────────────────┐      ┌──────────────────────────────┐
│  Next.js app (web)   │◄────►│  Supabase (Postgres + Auth)  │
│  Capacitor (Android/ │ REST │  - PostgREST (auto REST API) │
│  iOS, static export)  │      │  - Row-level security         │
└─────────┬────────────┘      │  - SECURITY DEFINER functions │
          │                    └──────────────────────────────┘
          │ fetch()
          ▼
┌─────────────────────────────────────────────┐
│ Quran.com API v4 · Aladhan API · hadith-api  │  (third-party, read-only)
└─────────────────────────────────────────────┘
```

- **Web deployment** (e.g. Vercel): runs the full Next.js server, including
  the two API routes below.
- **Native app** (Capacitor): a static export with no server of its own
  (`scripts/build-capacitor.mjs` strips `src/app/api` and the proxy out of
  that build). It calls the *hosted* web deployment for those routes via
  `getApiBaseUrl()` in `src/lib/api-config.ts`.
- The browser only ever holds the Supabase **anon** key
  (`NEXT_PUBLIC_SUPABASE_ANON_KEY`). Every permission is enforced in Postgres
  by RLS — the anon key alone can do nothing destructive.

## Authentication & authorization

- **No user accounts.** Readers never sign in. Everything personal lives in
  the device's `localStorage` (see [On-device data](#on-device-data)).
- **Admins only**: the admin dashboard (`/admin`) uses Supabase email +
  password sign-in. Admin status is a row in `public.admins`, added via
  `add_admin(email)` by an existing admin, and checked server-side in
  Postgres by `public.is_admin()` — never trusted from the client.
- **Authorization** is enforced by RLS policy on every table, not by
  application code. A compromised or buggy frontend cannot bypass it.

## Database schema

Defined in one idempotent, re-runnable SQL file: `supabase/schema.sql`.

| Table | Purpose | Write access |
|---|---|---|
| `announcements` | Home-page banner | admins only |
| `feedback` | User-submitted feedback | anyone can insert; admins manage |
| `content_reports` | "Report a mistake" on Quran/hadith/guide content | anyone can insert; admins manage |
| `page_views` | Anonymous daily page-view counter (no IP/user id) | via `track_page_view()` only |
| `admins` | Who has admin access | via `add_admin`/`remove_admin` only |

## On-device data

Stored in `localStorage` only, never sent to the backend:

| Key | Contents | Code |
|---|---|---|
| `quran_bookmarks`, `quran_progress`, `quran_settings` | Bookmarked surahs, reading progress, reading settings | `src/context/*Context.tsx` |
| `nq_notes` | One note per ayah (max 2,000 notes, 4,000 chars each) | `src/lib/notes.ts` |
| `nq_collections`, `nq_collection_ayahs` | Collections incl. the default Favorites (max 50 collections, 1,000 ayahs each) | `src/lib/collections.ts` |
| `nq_reading_history` | Recently read ayahs, newest first, capped at 200 | `src/lib/reading-history.ts` |
| `quran_reciter`, `tafsir_id`, `hadith_language`, `prayer_alerts`, `last_listening` | Preferences and resume point | various |

Every read validates the stored shape (corrupted data is ignored, never
crashes the app) and every write fails soft with a friendly "storage may be
full" error. Saved Quran text/tafsir for offline reading lives in IndexedDB
(`src/lib/offline-store.ts`).

## RPC functions

Called via `supabase.rpc('name', params)`. All are `SECURITY DEFINER` with an
explicit `auth.uid()`/`is_admin()` check inside, and `revoke all ... grant
execute ... to authenticated` (never `anon`, except where noted).

| Function | Who | Purpose |
|---|---|---|
| `is_admin()` | anon, authenticated | Whether the caller is an admin (used inside other policies/functions) |
| `add_admin(email)` | admins only | Grant admin access to an existing user |
| `remove_admin(user_id)` | admins only | Revoke admin access (can't remove yourself) |
| `track_page_view(path)` | anon, authenticated | Increments an anonymous daily counter; silently no-ops for `/admin*` or malformed paths |

## Custom REST routes

Only two — everything else is the Supabase surface above.

### `GET /api/download-audio`

Streams reciter audio through this server instead of the browser fetching
the CDN URL directly, so the mobile "Download" feature works from a CDN with
strict CORS. **Not an open proxy**: only `quran.com`/`*.quran.com`,
`qurancdn.com`/`*.qurancdn.com` and `download.quranicaudio.com` are allowed,
HTTPS-only, no redirects followed, response must be `audio/*`, capped at
200MB, and rate-limited to 20 requests/minute/IP.

| Query param | Required | Notes |
|---|---|---|
| `url` | yes | Must be an allowed HTTPS audio host |
| `filename` | no | Suggested download filename (sanitized, ≤100 chars) |

Responses: `200` (audio stream), `400` (missing/invalid `url`), `403` (host
not allowed / URL had credentials or a non-default port), `413` (too large),
`429` (rate-limited), `502` (upstream fetch failed).

### `GET /api/health`

Liveness/readiness probe for the hosted web deployment.

```json
{ "status": "ok", "timestamp": "2026-01-01T00:00:00.000Z", "checks": { "supabaseConfigured": true } }
```

Deliberately does not call out to Supabase or Quran.com — a health check
that depends on third parties turns *their* outages into false alarms about
this deployment. It reports whether Supabase is *configured*
(`NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` present), which is
what a deploy actually controls. Always `200` with `Cache-Control: no-store`.

Neither route exists in the Capacitor (native app) build — `output: 'export'`
can't serve API routes, so `scripts/build-capacitor.mjs` removes `src/app/api`
for the duration of that build. The native app calls the hosted web
deployment's copy instead.

## External APIs

| Provider | Used for | Where |
|---|---|---|
| [Quran.com API v4](https://api.quran.com/api/v4) (`api.quran.com`) | Surah/ayah text (Uthmani script), translations, tafsir, reciter audio, verse search | `src/lib/quran-api.ts`, `src/components/SearchModal.tsx` |
| everyayah.com / quranicaudio.com mirrors | Per-ayah audio for reciters without Quran.com per-verse recitations | `src/lib/quran-api.ts` (`RECITERS`) |
| [Aladhan API](https://api.aladhan.com) | Prayer times, Qibla direction, Hijri calendar | `src/lib/prayer-api.ts` |
| [fawazahmed0/hadith-api](https://github.com/fawazahmed0/hadith-api) (via jsdelivr CDN) | Hadith collections | `src/lib/hadith.ts` |

All are allow-listed explicitly in the CSP `connect-src` directive
(`next.config.ts`) — nothing else can be fetched from the client.

## Running migrations

Paste `supabase/schema.sql` into the Supabase dashboard's SQL editor and run
it. It is idempotent (`create table if not exists`, `drop policy if exists` +
recreate), so re-running it is always safe.

Projects that previously ran the old account migrations can remove those
now-unused tables with `supabase/remove_user_accounts.sql` (optional).

## Security model

- **RLS everywhere.** Every table has `alter table ... enable row level
  security` plus explicit policies; there is no table a signed-in user can
  read/write outside their own rows (or, for admin tables, outside admin
  status).
- **No service_role key ships to the client**, ever — only the anon key,
  which RLS constrains. Verified in `src/lib/supabase.ts` and enforced by
  convention/comments throughout the SQL files.
- **Admin checks happen in Postgres** (`is_admin()`), not just in the
  frontend's admin UI gate — an admin route rendered by mistake still can't
  read/write anything a non-admin session couldn't.
- **Input validation lives at the boundary**: every text/jsonb column has a
  `check` constraint (length, format, or both).
- **No personal data on the server** beyond what a reader chooses to type
  into feedback or a content report.
- **`/api/download-audio` is not an open proxy** — see above.
- **Security headers** (`next.config.ts`): CSP, HSTS, `X-Frame-Options: DENY`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy`, restrictive
  `Permissions-Policy`.
- **Nothing sensitive is logged.** No password/token/API-key values ever
  appear in application logs (end users have no passwords, admin passwords
  are handled only by Supabase Auth, and the anon key is public by design).
